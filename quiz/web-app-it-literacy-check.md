# 第2章 Webアプリケーションの構造（8問）

## Q13. フロントエンドとバックエンド

「フロントエンド」と「バックエンド」の違いを説明してください。

このアプリではそれぞれ何を担当していますか？

### A13.

フロントエンドはユーザーから見えるWebサイトやアプリの画面のこと。このアプリではカードを表示させたり、カードの並び替えを行ったりしている。
バックエンドはそれらフロントエンドからの要求を受けてDBと通信を行うために、データの形を整えたり取得したりすること。
カードを表示するためにDBデータを取得したり、フロントエンドから受け取ったカードのデータをDBに保存できるようにデータの形を整え、保存処理をDBとやりとりしている。

---

## Q14. 3層構造

このアプリは

- フロントエンド
- バックエンド
- データベース

の3層構造です。

なぜこのように役割を分けるのですか？

1つのプログラムですべてをやらない理由を説明してください。

### A14.

それぞれの得意分野を活かすため。
フロントエンドは描画処理に優れているが、データの形を整えたり、データをずっと保存しておくことはできない。
バックエンドはデータの形を整えたりすることはできるが、画面描画は専門分野ではない。
DBはデータの保存はできるが、それ以外のことはできない。
そのため各プログラムで得意なことをやってもらっている。
また、それぞれで管理することによって、保守のしやすさが挙げられる。画面側の修正をするときでも、フロントエンドだけ修正することが可能。

---

## Q15. データの流れ

ユーザーが「新しいタスクを作成」ボタンを押してから、

- データベースに保存される
- 画面に反映される

までの流れを順を追って説明してください。

### A15.

※「新しいタスクを作成」ボタン押下で、すでに入力されたカードが保存されるものとする。
作成ボタン押下で入力されたデータと、保存してくださいというAPIがバックエンドに渡される。
渡されたデータをバックエンドが受け取り、DB側に渡すようにデータの形を整える。
DBに保存してくださいという命令と共にデータを渡す。
DBがデータと命令を受け取り、命令を実行し、保存処理を行う。
保存が完了したら、成功（失敗したらその旨）のレスポンスをバックエンドに渡す。
バックエンドはレスポンスを受け取り、一覧照会するための命令をDBに渡す。
DBは受け取った命令を実行し、実行結果をバックエンドに返却する
返却値を受け取ったバックエンドは、フロントエンドが描画しやすいようにデータの形を整えてからフロントエンドにデータを渡す。
フロントエンドは受け取ったデータを元に画面を描画する（ここで保存したタスクが反映されているかどうかをユーザーは画面で確認する）

## Q19. 入力チェック（バリデーション）の多重防御

入力チェックはフロントエンドとバックエンドの両方で行うべきと言われています。

なぜ片方だけでは不十分なのですか？

### A19.

フロントエンドだけだと、APIを直接呼び出すなどして、入力チェックを回避される可能性が高いため。
バックエンドだけだと、入力ミスが通信を行った後でないとわからず、使い勝手が悪くなる（送信してエラーが返ってきて初めてわかる。）
そのため、フロントエンドでは利便性、バックエンドでは安全性のために入力チェックを行う。

## Q27. トランザクション

トランザクションとは何ですか？

タスクを別カラムへドラッグ移動する操作で、なぜ重要ですか？

### A27.

一連のデータベース処理を、「全て成功」または「全て失敗」にする仕組みのこと。途中でエラーが発生した場合は、処理を元に戻してデータの整合性を保つ。
タスクとドラッグして別の位置へ動かす際には、タスクの並び順など複数のタスクのデータを更新することになる。そのため途中で失敗すると他のデータとの不整合が起きる可能性があるため、トランザクションの使用が重要となる。全ての更新が成功した場合だけ反映し、失敗した場合は元に戻せるためにトランザクションを使用する。

---

# 第4章 開発プロセスとチーム開発（4問）

## Q29. バージョン管理（Git）

Gitなどのバージョン管理システムとは何ですか？

なぜ必要ですか？

使わないとどんな問題が起きますか？

### A29.

バージョン管理システムとは、ソースコードの変更履歴を管理する仕組み。誰がいつ、どのような変更を行なったかを記録する。これにより、いついつ誰がソースを更新したかがわかるだけでなく、バグが生じた際には元に戻すことなどが可能になる。
複数人で作業する際には、変更内容を安全に管理・共有できるため必要となる。使用しない場合にはどれが最新のソースかわからなくなったり、お互いの変更を上書きしてしまったりするなどの問題が生じる。

---

## Q30. ブランチとPull Request

- ブランチとは何ですか？
- Pull Request の目的は何ですか？
- なぜ全員が main に直接変更しないのですか？

### A30.

- ブランチとは、各個人の作業スペースのこと。ここでの編集は他人へ影響しないため、お互いの変更を上書きする心配がなくなる。
- Pull Request の目的は、各ブランチをmainにマージする前に、レビュー者レビューして、修正したソースに問題がないかを見るためのもの。
- 全員が main に直接変更しないのは、Gitを使っていない状態と同じように、お互いの変更を上書きしてしまったり、オリジナルのソースコードを修正してしまっていることと同義のため。コピー（ブランチ）を作成してから修正を行なった方が、オリジナル(main)に影響が少ない。

---

## Q31. コミットメッセージの重要性

例：

`feat: ログイン機能を追加`

良いコミットメッセージを書くことがなぜ重要ですか？

### A31.

コミットメッセージを見ただけで、どのような変更が行われたか、なぜ変更したかを確認することができるため。メールの件名と同じようなもの。
レビュー者はたくさんの作業者のプルリクを見るため、忙しいことが多い。レビュー者がパッと見て理解できるように書くことが望ましい。
また、自分が過去に行ったコミットを見ても、何をしたコミットなのか分かりやすいようにしておくことが重要。昨日書いたコードは他人が書いたコードとほぼ同じ。

---
