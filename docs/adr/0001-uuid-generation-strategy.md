# ADR-0001: UUID生成戦略

- **状態**: 採用
- **決定日**: 2026-07-03

## 決定

エンティティのIDは、DBの自動採番（`gen_random_uuid()`等）ではなく、**JPA/Hibernateによるバックエンド側で生成する**。

```java
@Id
@GeneratedValue(strategy = GenerationType.UUID)
private UUID id;
```

## 背景

Board・TaskList・Card の各エンティティにUUIDの主キーを採用するにあたり、
生成責務をバックエンド（JPA）とDB（PostgreSQL）のどちらに持たせるかを検討した。

## 理由

### 採用した理由（バックエンド生成）

1. **INSERTより前にIDが確定する**
   Board → TaskList → Card のような親子関係を持つエンティティを保存する際、
   DBへの問い合わせなしにメモリ上で関連付けを完結できる。
   途中でDB例外が発生しても、ロールバック前の状態が一貫している。

2. **Hibernateのバッチ最適化をそのまま活かせる**
   `hibernate.jdbc.batch_size` によるバッチINSERTは、ID確定済みであることを前提とする。
   DB生成方式ではINSERTのたびにIDを取得する追加ラウンドトリップが発生し、バッチ効率が下がる。

3. **DBに依存しない**
   PostgreSQL固有の関数（`gen_random_uuid()`）に依存しないため、
   テスト用のH2や将来的なDB変更に対しても設定変更なしに動作する。

4. **一意性は実質保証される**
   UUID v4の衝突確率は1秒間に10億個生成し続けて100年後に初めて衝突するかどうかのレベル。
   シングルユーザー・シングルサーバーのこのアプリでは問題にならない。

### 不採用とした理由（DB生成）

- DBへの追加ラウンドトリップが発生し速度が下がる
- PostgreSQL固有関数への依存が生まれる
- バックエンドでINSERT前にIDを参照できない
- このプロジェクトではDB直接INSERTのユースケースがないため、DB生成のメリットが活きない
